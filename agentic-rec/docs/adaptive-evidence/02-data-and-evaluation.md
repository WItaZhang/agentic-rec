# 02 · 数据与评估协议

[返回设计入口](README.md) · [上一篇：方法](01-problem-and-method.md) · [下一篇：实现](03-implementation.md)

本文件定义拟实现的主实验协议。任何改变目标定义、可见信息、候选空间、切分或聚合方式的调整，都需要新的 `protocol_id`，不能覆盖旧结果。

## 1. 数据选择与两条协议

### 1.1 MovieLens：工程验证

复用 [PR #1](https://github.com/WItaZhang/agentic-rec/pull/1) 的 MovieLens 100K 实验基础，先复现 Popularity，再增加 ItemKNN。

该 PR 的协议在检查点 `ad358061d001cc2c039d905dfc58c38aa2c14b03` 使用全局时间切分、固定训练历史、时间窗口内多个正例、全候选排序。它用于检查加载、切分、指标和产物是否可信。

它没有实现本设计的逐事件回放、控制器或 LLM 文本证据实验。不要把已有多正例 NDCG 与下一物品 NDCG 放在同一改进百分比中。接入本设计时给旧协议加一个清晰的版本标识，而不是悄悄改其定义。

### 1.2 Amazon Reviews 2023：主实验

[官方数据页](https://amazon-reviews-2023.github.io/)提供评论时间、评分、文本与商品属性；用户—物品事件和商品元数据使用明确记录的 ID 连接（通常需要 `parent_asin`）。

先选择一个品类。选择依据只看训练期数据覆盖和工程预算，不看测试模型效果：

- 在训练截止点之前，有多少用户具有可用历史？
- 不同历史长度的用户数量如何？是否足够做预定分组？
- 商品标题、类别、属性的缺失率如何？
- 训练期候选空间的大小和内存需求如何？
- 冷物品、重复消费、异常时间戳和稀有用户占比是多少？
- 原始数据的获取、使用与分享条件是否允许计划中的产物？

不要先假定某个小品类一定适合序列实验。品类小也可能意味着绝大多数用户只有一次行为。生成 `dataset_profile.json` 后再锁定主品类，并记录选择理由。

第二个品类用于检查外推性，应在主品类流程稳定后增加。第一份可信结果不要求同时覆盖多个品类。

## 2. 目标与事件定义

建议主协议名：`amazon_next_positive_unseen_v1`。

| 项目 | 拟定规则 |
|---|---|
| 交互 | 数据集中有时间戳的用户评论/评分事件，不解释为真实曝光日志 |
| 正反馈 | 初始建议 `rating >= 4`；在配置中固定，并报告评分分布 |
| 预测目标 | 时间顺序中满足正反馈条件且此前未交互的物品 |
| 历史输入 | 目标之前的所有允许反馈，保留反馈值；正/负反馈不能混作等价喜欢 |
| 已见排除 | 候选中排除该用户此前任何已交互物品；与目标的“未见”定义一致 |
| 重复事件 | 精确重复去重；重复物品后续事件可更新历史，但不作为主协议的未见物品目标 |
| 冷用户 | 保留在总体评估，使用明确回退；单独报告历史为零的分组 |
| 冷物品 | 若目标不在冻结候选宇宙中，仍作为 miss 进入主指标分母 |
| 无效记录 | 缺失核心 ID、非法评分、无法解析时间戳按确定性规则排除并统计 |

目标是“下一次被观测到的正反馈物品”，不是全部相关物品的完整标注；未交互物品不应称为真实负例。训练中的负采样也只是算法近似。

同一用户同一时间戳可能有多个目标。主协议建议将它们作为具有相同历史前缀的多个单目标请求，全部预测完成后再公开该时间戳事件；报告并列事件比例。不得通过行号顺序让同时间事件相互泄漏。若改为多正例集合目标，要升级协议并重新定义指标。

## 3. 四段全局时间划分

```text
               T0                 T1                T2                T3
base_train     | policy_train     | validation      | test            |
基础模型训练    | 生成方案标签      | 选择配置和预算    | 最终报告         |
```

- `base_train`：`timestamp < T0`。
- `policy_train`：`T0 <= timestamp < T1`。
- `validation`：`T1 <= timestamp < T2`。
- `test`：`T2 <= timestamp < T3`，或明确记录的最终数据截止点。

时间边界采用 UTC，原始时间单位写入 schema。先根据时间分布和训练覆盖选择实际日期，再写入冻结 YAML；文档不提供未经数据检查的“通用日期”。相同时间戳不跨边界。

基础推荐模型的超参数在 `base_train` 内部用更早训练、更晚验证的子切分选择，再在整个 `base_train` 拟合。控制器使用 `policy_train` 的结果标签训练，超参数在 `validation` 上选择。第一版不在最终测试前重新拟合基础模型，避免候选和策略标签突然换分布。

后续若要使用更多数据重训，建立新协议：重新生成控制器训练所需的时间外预测与候选清单，重新选择参数，再评估。不能只更新基础模型却沿用旧路由标签。

### 3.1 允许历史增长，但模型权重冻结

在逐事件回放中，较早发生的验证/测试事件，在其发生之后可以成为后续请求的历史。这模拟固定模型下不断更新的用户状态。

要求：

1. 对时间 `t` 的全部请求，先以 `< t` 的视图执行预测。
2. 评估器记录结果，不把目标回传给当前 Agent 进行第二次尝试。
3. 当前时间戳的全部预测完成后，统一把真实事件加入后续历史。
4. 所有方法看到相同的外部历史；某方法推荐了某物品，不代表用户真的点击它。

这是预先规定的状态更新，不是根据测试结果更新模型。控制器参数、提示词、阈值、向量索引训练参数在测试期间冻结。

## 4. 不同信息的可见性

| 信息 | 主协议可见性 | 处理方式 |
|---|---|---|
| 用户历史评论和评分 | 事件时间严格 `< t` | 通过时间视图访问，不传入完整用户对象 |
| 当前目标评论、评分、商品 ID | 决策期间不可见 | 单独保存于 evaluator-only 标签表 |
| 其他用户的评论 | 评论时间严格 `< t`，且实验允许此工具 | 按时间过滤后选择；选择规则不能查看目标 |
| 行为统计、商品热度 | 指定训练截止点或严格 `< t` | 主版本优先训练期冻结统计；动态统计单独标记 |
| 用户画像、摘要、记忆 | 所有来源都早于 `t` | 存来源 ID、生成时间、历史水位和模型版本 |
| embedding / 近邻索引 | 构建输入符合所声明的时间范围 | 文本更新后重新索引或按版本访问；记录构建成本 |
| 标题、类别、描述 | 数据通常是爬取时快照 | 声明静态属性假设，做去除文本的敏感性分析 |
| 快照价格、平均评分、评分数、可售状态 | 不可假设预测当时已知 | 默认排除，或以可证明的历史值替换 |

静态属性假设不能让实验被称为完整历史线上重放：商品描述也可能事后编辑。报告必须指出这一限制。若某字段没有可靠的历史有效时间，标记为 `snapshot_assumed_static`，不要伪造历史时间戳。

LLM 预训练也可能包含公开商品信息。记录模型版本和评估日期，使用本地候选别名 ID，明确当前实验无法完全排除模型预训练知识的影响。

### 4.1 缓存键

缓存至少包含：数据版本、协议版本、用户/候选对象、请求时间或历史水位、证据选择器版本、提示词/模型版本。不能仅以用户 ID 缓存画像并跨时间复用。

将 `source_event_max_time >= request_time` 的证据视为错误，立刻失败。对无事件时间的静态元数据使用单独类型检查，不能让 `null` 绕过所有时序检查。

## 5. 候选生成

### 5.1 冻结候选宇宙

第一版候选宇宙为 `base_train` 期间出现的物品。未知新物品目标保留为 miss；它们需要另一套冷启动召回方法，超出第一版排序研究范围。

每个请求通过固定基础模型和可见用户前缀生成 Top-M。建议先试 `M=50` 或 `100`，`K=10`；以训练/验证阶段的召回覆盖和上下文成本选择最终值。这些数值是起点，不是已经采用的结果。

对于不能编码新历史物品的模型：忽略 OOV 编码并记录数量，或使用固定的内容回退。不同方法必须使用同一规则，不能隐藏冷启动请求。

### 5.2 固定清单与公平输入

生成候选后保存：请求 ID、候选 ID、基础得分、基础排序、模型版本、时间水位和候选清单哈希。所有策略读取同一份清单。

- 绝不根据测试目标把正例补进候选。
- 元数据缺失不能导致某个方法悄悄替换候选。
- Agent 工具返回其他物品时应拒绝或标为证据对象，不能加入推荐输出。
- 允许读取历史物品作为证据，但历史物品不因此变成可推荐候选。
- 候选数少于 M 时保留实际数量并统计，不使用目标信息填充。
- 主要比较沿用相同基础排序呈现；另做跨方法共享的随机呈现顺序实验，检查位置偏差。

比较不同召回器时，各自形成独立候选条件，分别报告召回和下游结果。不能让自适应方法独享更好的召回器。

## 6. 请求抽样

为了控制 LLM 调用，可以在完整事件协议上预先抽取请求清单：

1. 基于合法事件规则产生请求 ID，ID 不包含目标物品 ID。
2. 根据用户、时间段及前缀可计算的分层信息，用固定种子/hash 抽样。
3. 在任何策略调用之前冻结清单；不按目标是否召回成功抽样。
4. 记录抽样概率、每用户请求上限、各分组覆盖和排除原因。

开发烟雾实验可用约 100–200 个请求；正式数量根据方差、置信区间宽度和资源预算确定，不能把示例样本量当作足够统计功效的保证。小样本只支持可行性判断。

主报告采用用户宏平均：先平均每个用户的请求指标，再对用户平均。另报请求微平均和参与用户数；若过采样稀疏组，报告分层结果并给出明确的总体重加权方式。

## 7. 指标定义

对单目标请求 `q`，目标在最终 Top-K 的名次为 `rank_q`：

```text
HR@K(q) = 1 if rank_q <= K else 0
NDCG@K(q) = 1 / log2(rank_q + 1) if rank_q <= K else 0
CandidateRecall@M(q) = 1 if target_q in candidate_q else 0
```

单目标协议下 Recall@K 与 HR@K 相同，不将其描述为两个独立证据。多正例 MovieLens 协议仍使用其原本的 Recall 与理想 DCG 分母。

至少报告：

- 用户宏平均 NDCG@10、HR@10；预先定义次要 K 值时明确主次。
- CandidateRecall@M，包含冷物品目标的 miss。
- 条件重排指标：仅在目标被召回时计算，标为 `conditional_on_retrieval`，只能做诊断。
- 不合法输出、超时、回退、空候选率。
- 实际输入/输出 token、调用次数、工具次数、均值/P50/P95 延迟。

不能在计算主指标时排除失败请求、未召回目标、元数据缺失或 LLM 不喜欢的请求。固定回退产生什么排序，就据此计分，并保留失败标记。

## 8. 输出校验与修复

统一要求模型输出约束 JSON：`{"item_ids": ["c17", "c02", ...]}`。

主规则建议：

1. 解析失败时允许至多一次预先配置的修复调用，费用完整计入；也可以配置零修复。
2. 去掉非法、重复和池外 ID，同时记录原始失败类别。
3. 不足 K 时按基础排序补齐合法未输出项。
4. 完全无效、预算不足或最终超时，返回基础排序。

修复必须不读取真实目标。各方法使用同一解析、重试和回退规则，不能只为某个方法人工修复结果。

## 9. 最低限度的协议测试

- 在不同切分边界插入同时间戳事件，确认不会跨边界泄漏。
- 把目标评论和未来评论写入原始数据，断言工具无法读到它们。
- 在未来新增交互/改动未来文本，断言过去请求的候选与可见证据不变。
- 修改目标标签表，断言 Agent 输入、工具参数与策略动作不变。
- 构造目标未召回和冷物品例子，手算指标并确认仍进入分母。
- 构造重复目标、OOV 历史、空历史、缺失元数据与非法 LLM 输出。
- 请求级缓存倒序调用时仍返回正确的时间视图，不复用未来画像。

这些测试验证实验可信度，应优先于增加模型复杂度。完整实验矩阵与统计方法见 [04](04-experiments.md)。
