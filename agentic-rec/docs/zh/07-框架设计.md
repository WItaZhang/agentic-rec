# 07 · 框架设计

这一节把 05 节的九个组件变成代码接口，并记录每个设计决定背后的原因。建议边读边打开 `agentic_rec/` 目录。

## 1. 所有角色共用一个 Agent 骨架

```
Observation ──► profile.render ─┐
                memory.render ──┼─► PlanContext ─► planner.plan(tools) ─► Action
                task ───────────┘                        │
                                                          ▼
                    feedback ─► reflector.reflect ─► memory.add(insight)
```

`agentic_rec/agents/base.py` 里的 `Agent` 是唯一一个让所有组件相遇的地方。它的 `act(obs)` 方法做五件事：

1. 让画像把观察渲染成一段人设文字。
2. 让记忆按当前问题检索几条相关记录，渲染成文字。
3. 把人设、记忆、任务描述、工具集打包成 `PlanContext`。
4. 交给规划器。规划器可能调用工具零次或多次，最后返回一个 `Action`。
5. 把这次动作记进记忆。

`feedback(text)` 方法把反馈交给反思器，反思器返回的一句洞见写回记忆。

`RecommenderAgent` 只是固定了默认任务描述，加了 `recommend(user)` 这个便捷入口。`UserAgent` 保留同样的三部分（画像、记忆、决策过程），但决策过程叫 `UserPolicy`，因为用户侧需要一个透明的、基于规则的实现来做测试和奖励塑形。`ItemAgent` 是一段会自我改写的描述。

**为什么不用类继承体系？** 曾经考虑过 `RecommenderAgent`、`ConversationalAgent`、`PlanningAgent` 这样的层次。放弃的原因是综述显示论文之间的区别在于"挂了哪些组件"，而不是"是哪一种 Agent"。组合比继承更贴合事实。

## 2. 每个组件都可选

每个组件家族都有一个 `Null*` 实现和注册名 `"none"`。配置里没写的键表示"没有这个组件"，Agent 构造函数对每个部分都接受 `None`。规划器的默认值是确定性工具链，所以没有 LLM 的 Agent 也能工作。

这个默认值让经典基线（ItemKNN、流行度）和 Agent 系统住进同一个空间：基线就是"没有画像、没有记忆、没有反思、规划器为 `chain`"的 Agent。

一个细节：判断组件是否存在必须用 `is None`，不能用真值判断，因为空记忆的长度是零，`bool(memory)` 会返回假。这个 bug 在写测试时被发现并修复，`test_buffer_memory_len_is_not_truthiness_trap` 专门守着它。

## 3. 靠一个小小的上下文对象组合，而不是靠继承

`PlanContext` 携带渲染好的人设、记忆文字、任务、工具集，以及一个 `ToolContext`。`ToolContext` 持有观察、一个 `candidates` 列表（这就是 InteRecAgent 的候选总线）和一个 `scratch` 字典。工具读写 `candidates`；规划器在 LLM 的最终回答里没有物品 ID 时把它当兜底。

没有任何组件持有另一个组件的引用。唯一的共享状态就是这两个数据类，每一步都新建。

## 4. Agent 当工具

`AgentTool` 把任意 Agent 包装成工具。`ManagerOrchestrator` 于是就是一个普通的 ReAct Agent，它的工具是它的工人。`PipelineOrchestrator` 和 `VoteOrchestrator` 覆盖综述里另外两种拓扑。

因为经理是普通 Agent，它自己也可以有画像、记忆和反思器，这正是 MACRec 的设计所要求的。

## 5. 注册表加纯字典配置

组件按 `(类别, 名字)` 注册。配置是嵌套字典；TOML 是默认格式，因为它在标准库里；JSON 也接受；装了 PyYAML 就支持 YAML。

`registry.create` 会检查构造函数的签名，只把共享对象（`llm`、`catalog`、`k`）注入到声明了同名参数的构造函数里。所以组件永远不必声明自己用不到的参数。

扩展方式：继承、用 `@registry.register("tool", "my_tool")` 装饰、在配置里写 `"my_tool"`。`examples/04_custom_component.py` 演示了一个工具和一个记忆。

## 6. 不依赖 SDK 的 LLM 后端

`LLM.complete(prompt)` 和 `LLM.chat(messages)` 就是全部接口。`OpenAICompatibleLLM` 和 `AnthropicLLM` 用标准库的 `urllib`，所以整个包零运行时依赖。

`MockLLM` 是一套针对框架自身 prompt 格式的确定性策略。它让整个流程、编排和评测都能离线跑，测试和持续集成用的就是它。它不是对用户行为的建模，README 里明确写了这一点。

## 7. 环境同时返回文字和奖励

`Environment.run_episode` 把每次用户反应转换成两样东西：（a）自然语言反馈，通过 `feedback()` 交给推荐器，闭合反思循环；（b）标量奖励，存进轨迹，供强化学习训练器消费。

两个视图并存的原因：综述里 2023 到 2024 年的系统靠文字适应，2025 到 2026 年的系统靠奖励适应，环境不应该替使用者做这个选择。

## 8. 刻意不做的事

- **不含训练循环。** 强化学习和监督微调依赖模型运行时；框架暴露轨迹和奖励，到此为止。
- **不含向量数据库。** `VectorMemory` 接受一个 `embed` 回调；默认是词袋余弦相似度，这样检索语义不需要模型就能测试。
- **不下载数据集。** `make_synthetic` 提供一个带已知隐藏偏好的目录；MovieLens 或 Amazon 加载器就是一个 `Catalog` 加一组 `User`，属于用户代码或后续工作。

## 9. 怎么看待那些论文复现配置

`configs/*.toml` 把论文映射到组件选择。它们是**结构**复现，不是数值复现：工具是合成目录上的 item-kNN 和流行度，mock LLM 走固定策略。它们的目的是证明十一个已发表架构是同一配置空间里的十一个点，并在需要真正复现某篇论文时提供起点。
